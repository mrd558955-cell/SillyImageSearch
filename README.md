# Image Search for SillyTavern

Click the images icon next to the chat box (or the wand menu, or `/imgsearch tags`) to open a picker. Tags are suggested by a small model from the latest messages, pictures come from the image boards you list in the settings, and the one you pick lands in the chat box without being sent.

## Settings

The settings are in folding sections (Setup, Picker, Saving and library, Descriptions, Picture send, Filing and looks, Advanced, Delete everything); each shows a one-line summary when closed, and the box at the top finds any setting by a word in it.

## Setup

1. In API Connections, pick a fast model that does not think (e.g. NanoGPT `deepseek/deepseek-v4.1-flash`), save it as a connection profile called `Tags`, then switch back to your main profile.
2. In the Image Search settings, choose `Tags` as the tag profile.
3. List image boards, one per line (e.g. `safebooru.org`, `danbooru.donmai.us`). Gelbooru, Danbooru, e621, Moebooru, Philomena and Shimmie sites (through their Danbooru-style address, e.g. `rule34.paheal.net`) are found on their own (e621's new post format from November 2026 is read directly, and the old one still works).
4. For the AI to see picked pictures: keep "Save picked pictures" and "Attach saved pictures" on, turn on "Send inline media" in the Chat Completion settings, and use a main model that accepts images.

Saving pictures needs `enableCorsProxy: true` in `config.yaml`, or the Cloudflare image fetcher.

For a site that refuses SillyTavern's server (403) or asks for a key, make an account there, copy the API key from your account settings on the site, and put it under Setup → Site accounts with your name (on Gelbooru, your user ID). Every site in your list gets a row there, and what you enter stays in your settings. The key is sent the way that kind of site expects (Danbooru and e621: login and api_key; Gelbooru: user_id and api_key; Moebooru: login and password_hash; Philomena: key), and SillyTavern's server tells the site honestly that it is SillyImageSearch for your account (`SillyImageSearch/<version> (user <name>; +https://github.com/mrd558955-cell/SillyImageSearch)`). A key pasted as the whole address a site shows (`site.net/profile.json?api_key=…&login=…`) works too, in the list or in the key box. Each row also has a Kind choice (Danbooru, e621, Gelbooru, Moebooru, Philomena, Shimmie, or find out by itself): with a kind chosen, the extension asks only that kind of address on the site, instead of trying each kind in turn. "Check every site" (or Check on one site's row) lists every address it tried with what each answered (keys hidden), then tries one small search and says what each site needs, and how SillyTavern's server said who was asking ("Sent as: SillyImageSearch/… (user …), with your key"): it works, it refuses (add or check the account), it asks to slow down, or a Cloudflare check stops SillyTavern's server (an account sometimes gets through; otherwise only the site can let SillyTavern in).

Saved by mistake: in the search grid, tap a gold bookmark once (it turns into a red bin) and again within 3 seconds to take that picture back out of the library; in the preview, "Remove" (tap twice) next to "In library" does the same. Both only work on single pictures; one in a saved set or sequence is removed from there in the library.

Duplicates: the copy button in the library bar checks every single picture (the first time it reads each file once; after that it is quick) and shows the duplicates in coloured groups, newest first: the same post, the same file (from any site), or pictures that look the same (resized, recompressed or slightly cropped copies; the colours must match too, so different pictures with a similar layout are not grouped). Open one to compare, or tap × twice to remove it; Done goes back to the library. Sets and sequences are not checked.

Characters: the cast of a chat comes from the character card, the character's and the chat's lorebooks, and the preset's tracker. A card that describes several people (an RPG bot) is split into one character each; lorebook entries that describe a person become characters too (their keys count as other names); a new name in a tracker line (`Name | Agenda: … | … | Body: …`) becomes a character made by the story, whose looks come from the message where the story introduced them. Each card and lorebook is read once with the tag profile ("Prompt for finding characters", editable), again only when it changes. Characters count for a picture when they are in the scene: named in the last two messages, their lorebook entry just used, or on screen in the newest tracker line (Body: Off-screen means not there). Send with a picture lists the characters in the scene first, then the rest of the cast. "Characters (Image Search)" in the chat's extensions menu (the wand), or the people icon next to Main focus in Send with a picture, opens the cast right in the chat; "Characters' looks" in the settings shows the same, with where each one comes from; "Read the characters again" reads them anew.

Appearance tracker: the extension builds the Appearance line for your preset and shares it as the global variable `stisAppearanceTemplate`: every look field of the filing (your own ones too), in their order, each listing its tags ("Hair: [black/brown/blonde/… or N/A]"), plus one Other field for 1 to 3 short sentences on what the tags cannot show (injuries, accessories, details). Before each reply it also fills the chat variable `appearanceTemplate` with the whole block in the same style as other preset blocks (`<details><summary>👗 APPEARANCE</summary><br>- <b>[Name]</b> | …<br></details>`), so a preset that gathers its blocks with `{{getvar::appearanceTemplate}}` gets it without a `setvar` of its own (setting: "Fill the preset's appearance template"). It follows your filing fields by itself. Lines whose name has symbols (like "Marcus ↔ User") or whose fields are all numbers (stats like BONDS) are never taken for people. Every reply's Appearance lines are read: values go straight into the look sheets (mapped with the filing's word lists, no extra request), a field left out keeps its last value, N/A leaves the card's value, and every change is remembered (shown in the Characters window). A line written with a first name ("Naruto") belongs to the full name. A sheet you edited keeps your values until the story changes that field after your edit. Before each reply, the last known looks of the people in the scene or named in the last messages are shared as `stisAppearanceLast`, so someone who comes back keeps their look. Appearance lines never decide who is in the scene; only a location field does (Body: On-screen / Off-screen).

Search tabs: the row of tabs under Search/Library holds up to 6 searches, each with its own tags, site and results. + opens a new empty tab; tapping a tab goes back to it with its results and scroll as they were (no new search); × closes it. The first tab is the main one: it gets the tags suggested from the story when the picker opens; the other tabs keep their tags for next time.

For a site whose Cloudflare check stops SillyTavern's server even with an account, tick "Through Firefox" on its Site accounts row. The SillyImageSearch Fetcher, a small Firefox add-on in the `firefox-fetcher` folder, then asks that site from Firefox itself: your own browser, with the pass you got there, as if you browsed the site, only when you search, one request a second, and only for sites you allowed in it (it shows an Allow page the first time). Searches, thumbnails, previews and saved pictures of that site all go through it; videos are downloaded by it too and played from that copy; pictures load 4 at a time, and each one is loaded once per search window (switching pictures in a group or the preview reuses it). When the site stops requests from the add-on itself, it asks from a quiet tab of that site instead (one per site, closed after 2 minutes unused); when even that gets the check, that tab shows the blocked address once so you can pass it, then Firefox goes back to SillyTavern. To install it, see `firefox-fetcher/README.md` (Mozilla signs it for free in a few minutes; then Firefox → Settings → Install extension from file).

Pixiv has no public way in for programs, so it goes through the Pixiv bridge, a small SillyTavern server plugin (in `server/pixiv-bridge` here). It uses your own Pixiv login and says honestly what it is (`SillyImageSearch-PixivBridge/1.0.0 (SillyTavern server plugin; +https://github.com/mrd558955-cell/SillyImageSearch)`); your login stays on the server, in SillyTavern's data folder, and is never sent back to the browser. It asks Pixiv only when you search, open a work or save one, one request at a time about 1.5 s apart; searches are kept for 15 minutes; when Pixiv answers "slow down" (429 or 403) it pauses by itself (2 minutes, doubling up to 30) instead of trying again; and it stops at a daily limit you set (400 requests by default). Nothing runs in the background for Pixiv: no group checks while scrolling, no tag lookups, no prefetch, and Pixiv is never part of All sites. To install it on ST-android, where the plugins folder cannot be reached: Manage ST → install from GitHub → `mrd558955-cell/SillyImageSearch`, branch `sillytavern-pixiv` (SillyTavern 1.19.0, unchanged, with the plugin in its `plugins` folder; your data and config are kept), then set `enableServerPlugins: true` with "Edit ST config" and start SillyTavern again. Elsewhere, put `server/pixiv-bridge` in SillyTavern's `plugins` folder. Then, in Setup → Pixiv: tick "Search Pixiv", paste your PHPSESSID (from a browser logged in to Pixiv; needed for R-18, bookmarks and follows) and press Log in. "Pixiv" is then a choice next to the sites in the picker, with its own filters (Kind: all, illustrations, manga, animated; Order; Match: part of a tag, whole tag, title and caption; AI: show or hide) and Bookmarks and Following; a pasted Pixiv link (a work or an artist) opens it. Results show Pixiv's tags with their English translations. A work with several pages shows its page count and its pages in the strip (Save set keeps them together); Pixiv animations are turned into GIFs on your device when saved (frames and timing kept). Pictures are saved at Pixiv's 1200-pixel size.

Danbooru asks programs to say whose they are (a user agent with `user #<your account number>`) and puts programs that pretend to be a browser through a Cloudflare check. Put your Danbooru account (name or number) in Setup → Danbooru account: SillyTavern's server then tells Danbooru it is SillyImageSearch for that account, for searches, thumbnails, previews and saving. No API key is needed. This works in Firefox; Chrome and browsers built on it do not let pages set it, so Danbooru still blocks pictures there, and the settings say so. If a site's image server blocks its pictures (Danbooru's cdn.donmai.us sometimes asks for a Cloudflare check), Danbooru pictures are first tried from Danbooru's own site (the same file under danbooru.donmai.us/data). If that is blocked too, the picker says so instead of showing an empty grid: "Pass the check" opens the check right in the picker, and once it is passed the pictures load again by themselves ("open it in a new tab instead" is there for browsers where the check stays blank). Saving goes through SillyTavern's server, which cannot pass such a check, so saving from that site may fail until the check is lifted. With more than one image board listed, "All sites" in the picker searches them all at once; the site switches under the tag box leave some out. Each site has its own words (uzumaki_naruto on one, naruto_uzumaki on another, female instead of 1girl on e621), so before a search each required tag is checked on each site: when the site does not use it, its own word is found from the other order of a two-part name, your links ("Same tag, written differently"), the site's aliases, and last the Tag model, which chooses among the site's real tags (or names one, which is used only if the site has it). What is found is remembered and listed under Setup → "Tags across sites", where you can remove it or add your own; the status line says which words were swapped ("naruto_uzumaki → uzumaki_naruto") and which tags a site has no word for. Preferred and left-out tags only use what is already known, with no extra request. Typing two letters or more in the tag box suggests matching tags from the sites, favorites first.

A site picture's preview is laid out like the library's: the arrows and Open post, then Use this as the wide main button, then Save to library and Save set side by side. Scroll down in a picture's preview to see all its tags: select some to add them to the search, mark them as favorites (the ★ row under the tag box), or leave out pictures that have them. The left-out list is in the settings ("Leave out pictures with these tags").

## Library

Pictures you pick are kept in the library (Library tab in the picker). Single pictures are offered to the AI through the lorebook "Image Search Pictures" (each entry starts with the lorebook rule, editable under "Lorebook rule" in the settings: how to show a picture, and that a picture can be shown when what happens fits even if the people look different from the characters); sets and sequences come only through the picture send, unless "Also offer sets and sequences" is on (then each gets one entry with a line per item). Under the library search, All / Singles / Sets / Sequences shows one kind in one tap; Order puts the pictures that fit the chat first (Best fit), the last saved first (Newest) or the last sent first (Last used); Clear all removes the search and every filter to show the whole library; the grid button switches between 2 and 3 pictures per row (kept for next time). The library grid and the items strip show small still copies of the pictures (made on your device the first time a picture comes near the screen, one at a time, and kept in the browser), so scrolling a big library no longer loads every full file and GIF at once; GIFs still play in the grid, but only the ones on screen (6 at most) and only while they are there ("Play GIFs in the library"; off: stills with a play badge). In the library you can redo a picture's description or delete it (the file is deleted too). Deleting a picture from a message no longer deletes a library picture's file: SillyTavern's "Also delete files from server" is unticked for it (setting: "Keep library files when a picture is deleted from a message"). If a library file is gone anyway, open the picture on its site in the picker and tap "Download again" (or Use this): the file comes back where it was, with its description. When a saved picture has fewer than 10 tags (paheal pictures often do), the extension looks for it on your other sites before describing it, and on Danbooru too once your Danbooru account is set (even if Danbooru is not in your sites list). First the same file (by its md5). Then its names are put into each site's own words: on Danbooru the artist is found under its Danbooru name (paheal often spells it differently), two-part names are tried in both orders (naruto_uzumaki / uzumaki_naruto) and aliases are looked up; names a site does not know are left out of the search but kept on the picture. The artist (or, without one, the rarest name) is then searched with each other name, rarest first, and the pictures of about the same shape are compared by look; a GIF is compared by 4 frames spread from start to end, so a match on any frame counts. The first picture close enough wins and the search stops. Then IQDB, a free lookalike search. Last, the vision model looks at the picture and gives a few specific tags (hair colour or style, eye colour, clothing, objects; never wide ones like 1girl or solo), each tried with the artist; after that it gives up. From a match it takes the tags of the whole group (parent and children), except for a GIF whose group has a video version: then only the video's tags. The tags found are added, so the description and filing card get them; the preview and the toast say what was searched and what matched, or link the closest pictures when nothing was close enough. "Find tags" in the preview and "Find tags for pictures with few tags" in the settings do the same by hand. For GIFs, the settings choose how many frames the vision model gets (1 to 32, spread from start to end, 3 by default), their size, and whether they go as numbered sheets instead of separate pictures. A sheet holds 4 frames (2×2) so each frame stays big; more frames make more sheets (up to 8), numbered in order across them. "Most pictures in one request" (8 by default) caps how many pictures go at once: frames are cut to fit, the second look sends fewer items per request, and a refused request is tried again with 4 frames before falling back to the first one. Lock keeps a good description: from then on Update (and "Redo all" or "Redo out-of-date descriptions") only brings the locked text up to the current description format, keeping what it says, instead of starting over; unlock to describe the picture from scratch. The settings have "Redo descriptions" (with a choice beside it: everything, single pictures only, sets only, sequences only, cut-off descriptions only, the ones that failed last time, or the ones not made with your current description prompt; the button shows how many; after a run with failures, the status gives the last error) and "Delete everything". Redo works on two pictures at a time, but only one GIF at a time (GIFs take much more memory; on Android, too much can make the system close SillyTavern). While Redo descriptions (or Find tags for pictures with few tags) runs, the screen is kept on (Firefox lets go if you switch away, and it is asked again when you come back). Pictures sent to the vision model are made smaller when a request would be too large for the provider (about 3.5 MB; some, like NanoGPT, refuse bigger ones with "Request Entity Too Large"), and a request refused as too large is sent again once with smaller pictures. If a Redo is stopped or interrupted (Firefox closed, phone restarted), the button becomes "Resume redo (N left of M)" for that same choice and goes on with the pictures not yet saved; "Start over" drops it.

The picture button next to Send sends your message and makes the reply come with a picture from the library: the AI picks the one that best fits what happens next, you can check it first (Send / Another / Cancel), and the reply is written to match it. The first window asks who the picture is about, who else may be in it, and (optional) what the picture should be about: that quick prompt helps choose the picture, together with what is in the chat box. Then, with "Suggest ways to bring it in" on (it can be unticked for one send in that window), the Tag model reads the story, the chat box, the quick prompt and the picture's whole description, and writes 3 ways for the story to get to the picture's moment, blending the two (things can be bent on either side so they fit; for a sequence item it knows what the next item shows). Edit one, write your own in the empty box, ask for New options, or send Without; the one you choose goes to the reply's AI. A swipe or a regenerate of that reply sends exactly the same again (picture, way in and all), even after you deleted the reply, went back to an older swipe, or deleted newer messages to come back to it. Once a sequence has started in the chat, its next item gets +100 points, so it is at the top of the pictures the AI compares and of the list when the AI does not choose. Pictures already shown and how far a sequence has gone are read from the chat itself, so deleting a message frees its picture and lets a sequence start over. With "Pictures between the lines" on, the reply's AI writes [picture] where the picture belongs and the picture is shown there, between the lines; if it forgets, the picture stays under the message. Pictures in your own message and the ones the AI shows on its own go where they were written too. The ways in and the AI that picks the picture get the last messages of the story with the newest one whole (up to 3,000 characters) and marked as already happened, and the start and end of the older ones; the ways in start after the newest message and never redo what it already shows. The reply instruction also tells the AI that the people in the picture may not look like the characters: it keeps the characters as the story has them and lets the picture's looks go, since what matters is what happens. Both prompts (the reply instruction and the ways in) are editable under "Picture send prompts". The lorebook also lists the pictures that fit the current chat best (re-checked every 10 messages), so the AI can bring one in by itself.

Each described picture gets a filing card from the tag model: who is in it (gender, species, skin, hair, build, outfit, features), pose, mood, place, framing and a few story moments it could illustrate. Filing cards (version 6) also carry a head count (everyone, also anyone only partly in view) and a rating (General, Sensitive, Questionable, Explicit), judged on everything the picture shows: nudity and sex, but also violence, blood, gore and anything disturbing. People are main (the one the description spends the most on, with every look field), side, or background; anyone partly in view says what is seen ("only a muscular arm"). Side people and people partly in view only get the look categories ticked "Also for side people" (gender, species and build at first; tick or untick any category, yours too, under Look categories), and they can only add points: a muscular arm against a muscular character adds the build points, anything else is 0, and all of them together stay under "Most another person can add". Only the main person can lower a picture's score. "Looks weight" (100% by default) lowers how much looks count against what happens; the cost of a missing main focus is never lowered. "Ratings it may send" holds back any picture or item whose card rating is not ticked: it is never sent, offered in the lorebook or shown to the AI that picks. A sequence item's meaning text names its place, role and intensity ("picture 4 of 6, the climax, intensity 9 of 10, a peak moment") and its whole story line. Both filing prompts are editable under "Filing prompts". Cards made before version 6 are redone in the background, sequences first and newest first; cards you edited are kept, and a card whose count differs from the description says so. The cards go into SillyTavern's vector search (NanoGPT embeddings by default, or the local model), so the picture button finds pictures by meaning, not shared words. Ranking is done in two steps: first by looks and keywords, then by meaning. Looks are scored by look categories you can edit under "Filing and looks → Look categories": each has a question for the AI, tags with the words that count as them, a type (same tag, ordered scale, each tag counts), what it is compared with (the character, your message, or both) and its points. Changing points costs nothing; changing tags or adding a category is filled in by "Update cards", which asks only for that category. On a tag line (`tall: tall, towering, above 6'4`), the words after the colon count as that tag when text is matched; the ones that describe it (with a number and a sign, like 6'4, or three words or more) are also given to every AI that picks a tag: the filing cards, the look sheets, the scene read and the preset's appearance template (cut at 60 characters per tag there, since it goes into every reply). Adding such a description marks the category changed: look sheets are redone, and "Update cards" redoes the cards. Built in: (gender, age group from child to old, species, hair colour, build, height, skin, eyes, features, outfit; close colours like black and brown cost less), filled once by the tag model from the whole character card (and your persona, when it counts) and editable under "Characters' looks". A mismatch costs about what a match earns, and a field the picture's card does not show costs 1. Pictures come in by two lanes: the best 50 by looks and keywords, and the best 50 by meaning (both settings). Only real meaning matches count: "Meaning strictness" (0.3 by default) is how close a picture's filing card must be to the scene, and pictures below it get no meaning points; "Test" searches a sentence (or the end of the chat) and shows the matches with a line where strictness cuts, so you can tune it for your embedding model. The meaning lane does not look at looks at all. Each picture gets looks out of 100 (against the best one, or 40 points) and meaning out of 100, plus the lower of the two, so pictures good at both win; being shown already, ruled out, the next of a sequence and the scene read are added on top. Of the pictures the AI compares, "Seats for looks" (50%) go to looks-only pictures and the rest to meaning-only ones; pictures in both lanes take any seat. The AI sees each picture marked [looks], [what happens] or [both], with an editable "Lanes note" (empty = no marks). "Read the scene first" asks the Tag model, at the same time as the meaning search, what kind of picture fits the moment: a rating, a pose, a mood and a value for each scene field. Pictures filed the same way get points: same rating +16, one step off 0, two or more steps off −16, the pose +4, the mood +4, scene fields their own points, all scaled by "Scene read strength"; its prompt is editable. What the search and the AIs read of the chat leaves out whole <details> blocks (a preset's internal states, appearance and bonds blocks), and any block names listed under "Left out of the story"; the meaning search reads the last 1000 characters of the reply before your message. A scene cut in your message ("the next day", "hours later", "---") leaves the old scene out, and actions your message rules out ("no kissing") push pictures showing them down. Pressing the picture button first opens a small window where you choose the main focus (a chat character or you, from your persona) and whether the others may also be in the picture. The main focus counts fully and a picture without them loses 20; the others add at most 5 and are not missed when absent; left out, the AI ignores them. The choice is remembered. The best matches go to the AI, which ranks every one of them with a short reason, shown on the card ("AI #3 of 30: …"); the card also shows how each picture was found and how long each step took. Cards can be read and edited in the library preview, and the Library tab has filters for type (animated), who, pose and mood. On the picture card, "Something wrong?" cancels the send and opens that picture in the library, to fix it. When the picture is the next item of a sequence already shown in this chat, the picture card says so ("Next of a sequence already shown in this chat: picture 4 of 6 · climax"), and the AI that ranks the pictures, the ways in and the reply instruction are told where it is in the sequence and what the picture before it was, so the story picks up from there ({{continues}} in the picture send prompts). "Library" on the picture card shows every picture in the order of this send, with its rank: a search box, All / Singles / Sets / Sequences, Animated, "AI's picks" and the filing filters (who, pose, mood) narrow it down. Its cells load as they scroll into view, and GIFs play there like in the library (only the ones on screen, 6 at most); everything is let go when the card closes. The pose and mood lists are in the settings, under "Filing and looks".

Videos show up with a play badge (turn this off with "Include videos"). In the preview, set where the GIF starts (type it, or play the video and tap "Start here") and its length, check it with "Play clip", then "Make GIF"; the GIF is made on your device and used like any picture. Making GIFs and finding parts need the pictures of the video. Some browsers give them (Chrome); Firefox for Android gives black or purple pictures instead. So the extension has a built-in video reader: FFmpeg built for browsers (`@ffmpeg/core` 0.12.10, GPL), downloaded once from cdn.jsdelivr.net, or unpkg.com if that fails (32 MB), checked against its known fingerprint, kept in the browser and run on your device; nothing is uploaded. "Reading videos" in the settings chooses Automatic (the built-in reader, or the browser if it cannot be downloaded), the browser, or the built-in reader. Videos play straight from the site. If that fails, or for Danbooru (which does not let the browser play them directly), the video is downloaded once through SillyTavern (with your Danbooru account for Danbooru) and played from that copy; the download is checked to be a whole video, and fetched again if it was cut short. If it still will not play, the preview says why (a page sent instead of the video, a damaged file, or a format this browser cannot play, in which case Make GIF and Find parts still work). Versions of a picture (parent and children on the site) share one cell with a group badge. A group that hides a video or GIF behind a still cover gets a play mark on that badge: from what the search found, and by asking the site for the rest of the group as the cell scrolls into view (two at a time). "Animated only" above the grid keeps only videos, GIFs and groups with one inside; groups not checked yet stay dimmed until they are. In the group strip, animated versions are marked. Next to it, "Videos … to … s" hides videos shorter or longer than the range (either box can stay empty for no limit; kept for next time); videos whose length is not known yet stay dimmed until it is read, and one whose length cannot be read stays shown. Each video shows its length on its badge: from the site when it says (Danbooru, e621), otherwise read from the start of the file as the video scrolls into view. Saved video parts show how much of the video they cover.

A video can also become several GIFs. "Find parts" reads the whole video (a few seconds with the built-in reader) and proposes parts: each loop as 3 full turns (set with "Loop repeats in a GIF"; fewer if they do not fit the GIF length), cut so the GIF loops without a jump (a move repeated only once or twice stays part of the action; a loop where one spot stops repeating, like someone starting to bleed, is split there, the second loop marked "with something changed"; when the same loop speeds up or slows down, that is a new part, marked "the loop before, faster"); what happens between loops, cut at scene changes and split to the GIF length; quick cuts close together (a fight's climax) kept together as "Fast action"; and still stretches. No part is shorter than 1.5 s. Black stretches and fades to or from black are left out, shown striped on the timeline. "Add clip" adds the clip set above by hand. The parts show on a timeline and as cards: tap a card to play that part from the video, looping (one at a time); move its start or end by 0.1 s or 1 s, split it where it is playing, merge it with the next one or remove it. "Make GIFs" makes them (any one can be made again), and the cards then show the real GIFs and their size. Save them as a sequence (parts in order: the AI shows them one after another) or as a set (separate moments: the AI shows whichever fits); up to 8 parts. Each part goes to the vision model as a sheet of frames and is described on its own, like the items of any set or sequence (below), so a part is only given the video's tags it shows. A GIF that took its tags from a video version on another site is told those tags cover the whole video. "Finding parts" in the settings sets how easily a loop is recognised. Leaving a video, switching tabs or closing the picker stops the video and frees it, and the built-in reader closes itself after a while unused, so phones (which can only play a few videos at once) keep loading new ones. The line under the buttons says how many pictures were read and how; when the browser reads the video, a small copy of it plays in the top left corner meanwhile. Length, width and frames per second are in the settings too.

In the library preview, "Correct" lets you say what is wrong in a description: only that picture or item is rewritten, knowing its role, intensity and story line and the group's shape, following your correction over the tags; the correction is kept, so later redos (and the story step) keep it. Attach a tag when you know what confused the AI: the tag goes to "Tags that matter" with your words as its tag note. Without a tag, the correction is only recorded (Settings → Corrections without a tag).

The library preview is laid out as: the picture, the items with their role and intensity ("climax · 9", ⚠ when a deduced tag waits to be checked), a progress strip while anything runs ("Working · step 4 of 7 · Writing the story lines", also shown as "4/7" on the library cell), the buttons Use this, Correct and Redo (the rest under ⋯), then folding sections: the description (open), the tags not found, Shape and overview, How this was described (with "Your tag notes at work": where your notes were sent and what was concluded, and the raw answers), and the filing card. The tags fold at the bottom behind an arrow. What you open stays open while you switch items.

The bookmark button on a picture saves it to the library in the background without adding it to the chat, so you can keep browsing.

"Select" lets you tap pictures in story order (from different searches and from the library) and "Save as sequence". The picture send shows them one at a time, in order, as the story moves on.

Some posts have other versions on the site (parent and child posts). They share one cell in the grid, with a count in the corner. Open it to see every version; "Save set" keeps them as one library entry.

New sequence steps (v3, on by default): sequences are described in another order (Descriptions → Sets and sequences → "New sequence steps (v3)"; off goes back to the steps described in the next paragraph, unchanged). First one request shows the vision model all the items together (a GIF as one sheet of 4 moments; if it refuses, still pictures, then one item at a time): for each item it says who is there (the same words for the same person, counting anyone only partly or just out of view) and what happens, which items show each of the sequence's tags (close enough counts), and which item feels like the emotional peak. In a sequence of separate pictures (not parts cut from one video), each picture keeps exactly its own tags from the site: the look at all the items gets them as hints and is not asked to place tags, and the step that reads descriptions for tags is skipped (only a picture with no tags of its own, or a sequence where every picture has the same tags, falls back to placing them). Instead, one text request ("Prompt for each picture's own tags", editable) checks each picture's description against its own tags: a tag its own description does not show becomes a tag not found for that picture, is judged like the others (the judge is told which picture had it), and in the panel "Not here" takes it off that picture only (Put it back gives it back); the gender facts are then checked per picture, from its own tags. In parts cut from one video, a picture's own post tags always count for that picture, and the site's own tag implications (Danbooru's, or e621's for e621; copied, never guessed, remembered for 3 months) add the tags they imply to the item that has the implying tag (an item with streaming tears gets tears). Each GIF's real length is read from its frame timings: its frames are picked by time, not by frame number, about 2 per second (at least 4, at most your GIF frames setting for the descriptions, up to 32 for the look at all the items, where the spare pictures go to the longest GIFs), and every step is told how long each GIF is; a GIF counts as a loop only when its last moment matches its first everywhere (one changed spot is enough to say no). Facts from the tags come first in every step: who the tags count, and when the tags count only boys (or only girls) and someone is called a girl (or a boy) with nobody of the counted gender left, the look at all the items is asked again and the item or story line is fixed (character tags' wiki pages give their gender too; the names are never used). Then each item is described in order, told what that look saw in it, what happens just before and just after, the description of the item before and the tags seen in it (with the definitions and your notes for the important ones); old roles are not passed on, so "Redo all" decides them afresh. Then one text request reads each item's description for the sequence's tags that item does not have yet (close enough counts, but never because another item has the tag), and adds each one it shows to that item only; "Tags added for this item" under the item lists the tags added by the implications or found in its description, with an × to take one off (Redo all will not add it again). The story lines are written with your story prompt. Loops: an item counts as a loop when its last moment matches its first, when Find parts says so, or when you set it with "Loop" in Edit role (Auto, Loop or Not a loop; your choice wins everywhere and survives Redo all), and loops show a repeat icon in the item strip. A loop is described with your "Loop note" (Settings → Descriptions → The rest of the description prompt), which can depend on whether the items before and after are loops; an item that is not a loop (set by you, or a video part) only gets the plain facts ("The item before is a loop. This item is not a loop. The item after is…"), and an item whose loop is not known gets nothing. The story step is told which items loop, and when every item but one is a loop, your "Story hint when only one item isn't a loop" (under the story prompt) is added; nothing forces the roles. Role fit (your rules), your notes (where a tag nobody saw most likely is) and a final check (each description against what the look at all the items saw; it never asks for a tag to be written in and never questions the roles) only collect what needs fixing: each item that needs anything is then looked at again once, with all of it, and a tag from your notes is placed only if the vision model keeps it ("Checked: … kept"), marked and revertible with Wrong. The story lines are then rewritten once, with the roles kept, and tags still not found are judged as before. "How this was described" shows the new steps, what the look at all the items saw in the item, a second opinion on the peak (and whether the story step agrees), what was looked at again and why, and how many requests the run took. Sets, single pictures, Redo item, Correct, Done and the intensity check work as before; on a sequence made with the new steps, they also get what the look at all the items saw. "What the AI saw" (under ⋯, on any described picture or item) shows the pictures the vision model got: for an item of a sequence made with the new steps, the sheets of the look at all the items and the frames of its own description, with the time of each moment in the GIF (or its frame number); exactly as sent during this session (the last 12 pictures), otherwise rebuilt from the GIF with your current settings. Settings → Descriptions → "The rest of the description prompt" makes every other part of it editable: the GIF note at the top (length, spacing, loop), the rules after your description prompt (picture first, people count, no names, your important tags' info), what the look at the whole sequence saw (new sequence steps) and the prompt for looking at an item again; each is filled with the default, a part between {{#name}} and {{/name}} is only kept when that thing applies, and Reset (or emptying it) goes back to the default. Under each set's title, "The prompt sent with these pictures" (open) shows the whole text the vision model got with them: exactly as sent for the pictures sent since SillyTavern was opened (the last 12), otherwise built again from your current settings (what would be sent now), and "Show it with my current settings" rebuilds an exact one to compare; opening the panel sends that prompt again with the same pictures (for the look at the whole sequence, with every item's pictures, as it was sent) and shows what the model says now, and you can edit the prompt and "Send again with this prompt" to try something else. Each set of pictures is also sent again on its own, with no words at all (no prompt, tags or context), and the vision model's quick answer shows under it, to tell a misread picture from a misleading context; a model that refuses pictures without words gets only "Describe this briefly." and the panel says so. On an item of a sequence, "Edit role" (next to Correct) changes its role, intensity and story line, and "Lock role" (or "Lock all roles") in the same place keeps them: Redo all, the story step and every story rewrite keep a locked role and intensity and fit the other items around it, and the item is described knowing its role.

Description sections follow your description prompt: besides Visual, Expression, Action, Atmosphere and Framing, any heading your prompt asks for on its own line ("Implication: …") becomes its own section, on its own line in the description, in the order your prompt gives. Each section can be up to 2500 characters.

Cut-off descriptions are caught: one that stops mid-sentence, stops before the headings your prompt asks for, or was cut at the old 700-character limit is marked with scissors in the library (filter: Check → cut off) and a red note in the preview; a fresh one also shows a warning. Raise "Description length (tokens)" and tap Redo.

Writing in a picture (speech bubbles, captions, signs) may help the vision model understand what is happening, but it is never quoted, translated or mentioned in a description; only sound effects like "BOOM" may be. A vision prompt you never edited is updated to this by itself.

Each picture or GIF in a set or sequence (an item) gets its own description. The site's tags are for the whole group, so they are first sorted out: the vision model looks at each item without the tags and lists what it sees; each real tag goes to the items where it was seen (tags it saw that the site does not have do not matter). A tag it wrote another way still counts: first through the links in Settings → "Same tag, written differently", then through the site's aliases (Danbooru and e621, checked once a month per tag), then, only for important tags still not found, one text request that links them to the words it used; each link is remembered, so next time the tag is matched at once, and you can remove links or add your own; a tag seen in no item is looked for again in all the items, four at a time. Each item is then described with only the tags it shows and the description of the item before it (so people and things keep the same names). Then one text request reads the descriptions for the tags still not found, with their definitions and your notes: a tag that a description already shows, in any words and even if a detail differs, goes to those items without changing their descriptions, so it is not judged as missing ("Already in the descriptions" in "How this was described"; Descriptions → Sets and sequences → "Tags in the descriptions" turns it off). Then one text request reads all the descriptions in order gives the group a shape ("setup → action → pause → climax") and each item a role, main and finer (setup, build-up, action, pause, climax, aftermath or transition, like "pause, standoff"; for video parts it is told where each part is and whether it is a loop or fast action). It first rates each item's intensity from 1 to 10, as a peak of emotion and not only of action (a reconciliation hug or a tearful goodbye can be the climax of a sad scene), and decides the climax from that: the item with the highest intensity, wherever it is; an item after it showing its result or a reaction is the aftermath. Item 1 is not always the setup, roles can repeat in any order, and a loop is how a part moves, not what it is. The ratings show next to each role ("intensity 8/10"), and the story step's raw answer is in "How this was described". Each item also gets a story line on what the moment means: what was happening, what is happening, and so what ("he slurps the last noodle, so he has just finished the bowl", not "the noodles are shorter"). Every description is told that the picture comes first: tags, notes and earlier descriptions only support it, and anything the picture does not show is mentioned only as likely off screen. Its Visual line starts with how many people or characters there are, counting anyone only partly in view (an arm, a figure in the shadows): "Two people (one only partly in view): …". The vision model is told what the count tags say (1girl, 1boy, solo_focus…; for an item, the group's tags) so it looks again when they count more people than it noticed. The main person gets the full description, each other person one short sentence. People do not vanish between items: each item is told how many people the item before counted, and to count someone hidden (behind someone, off screen, in the smoke) as out of view rather than gone; the final check flags a count that drops with nothing to explain it. Descriptions, story lines and overviews never use names, for single pictures too (he, she, the blond boy in orange), even when the tags give them, so the roleplay is not handed a new name; the final check flags any that slip through. Then "Role fit" checks each description against its role, with the rules you write under Descriptions → Sets and sequences → "Role rules" (left empty, the step is skipped): the roles are trusted, so an item whose description does not fit its role (a build-up describing the final blow) is described again as that role, with what it said and what it most likely shows instead, and the story lines are written again with the roles kept. From then on every rewrite of the story lines (after Done, Correct, Redo item, placed tags or the final check) keeps the roles and intensities; only "Redo all" decides them again. To test the intensity ratings, turn on "Intensity check (for testing)" under Descriptions → Sets and sequences, next to the story prompt: a sequence in the library then has "Check intensity", which runs only the story step on its current descriptions (one text request) and stops, and its preview shows each item's intensity as a bar with its reason, which item has the highest and which became the climax (in red when they differ), then the roles, the exact prompt sent and the answer; "Check role fit" checks the descriptions against your role rules without changing anything and shows each verdict. Roles and story lines are for sequences only: a set is versions to use on their own, so its items get no role. "Make it a set" / "Make it a sequence" (under ⋯, asks to be sure) converts a group and describes it again. Last, one request reads all the descriptions and story lines together, writes the overview and points out mistakes; an item with a wrong description is described once more, and wrong story lines are written again (it no longer questions the roles). Tags still found in no item (often cut off when the parts of a video were made) go to a prompt that judges whether they matter; if one does, the group is marked "Needs a look" in the library (a warning badge, and the Check filter). In the preview, the tags not found fold into one line ("Needs a look · 2 tags not found · 1 deduced"); open it and each tag is a single line with its state ("matters", "→ 2, 3 and after · note"), and tapping a tag opens only that one, with the judge's reason and these buttons: three choices: "Important" keeps it, "Not here" says it matters in general but not in this picture (it is taken out of the group, shown in red in the tag list where tapping it says why and "Put it back" restores it, it no longer counts for searches, and your reason goes to Settings → Important tags), "Doesn't matter" drops it everywhere; the item numbers place it in the items that show it, "Lasts after" also puts it in every later item (once it happened, it stays), and a note says why ("it happens off screen, because…"); a tag placed in several items gets one note box per item, or "One note" for all of them. Your choices are kept while you switch between items. Done updates only those items, keeping their descriptions (a locked one too) and telling the vision model what it missed, your note and the item's role, then writes the story lines again. Notes are saved with the tag, each with its item's role and story line, and item numbers in them are turned into roles ("item 3" becomes "the aftermath item") so they still make sense in another group (Settings → Tag notes, last 12 per tag; each can be edited, switched to "Lasts after" or removed, and you can add your own): in later groups, when nobody sees such a tag, one text request reads the story lines and your notes and places it where it most likely happens, if it is fairly sure (and in the items after, if it lasts). Those items are updated the same way (a lock is left as it is), the tags are marked (a wand badge in the library, a line on the item, a row in the panel, the Check filter "deduced"), and "Wrong" with a reason puts the items back as they were and saves the reason for next time; when a tag nobody saw looks like the cases where you said it did not apply, it can also be taken out the same way (marked, confirmed by Done, put back with Wrong); Done confirms the deductions you did not mark wrong, and each confirmed one is kept as another example. Your notes also go to the vision model when it looks again for tags nobody saw, as hints on how those tags show. A single picture's description also gets, for each of its tags in "Tags that matter", the definition and your notes, as hints (the picture still comes first). Each tag in "Tags that matter", and each tag not found in a group, also gets a definition copied word for word from the wiki of the picture's site (Danbooru, e621, Moebooru and Philomena sites have one), or from Danbooru's wiki when that site has none; aliases are followed to the main tag. Settings → Important tags lists the tags that matter: tap one to see its definition (read only, with a link to the wiki and "Fetch again") and everything you wrote about it (where you placed it, corrections, confirmed or wrong deductions, and when it did not apply), editable. Definitions and always come first, before your notes: when the vision model looks again, when tags are placed from your notes, when tags not found are judged, in the updates, and at the top of each tag in the panel. Your choices are remembered ("Tags that matter" and "Tags that do not matter" in the settings, editable): next time such a tag is judged by your choice without asking, and the others are judged with your lists as examples. "Mark as fine" clears the flag without changing anything. "How this was described" in the preview shows every step: what each item was given and seen, what was found again or placed by you, what was judged and what was fixed. The steps and the prompts (story lines for sequences and for sets, judging tags not found) are under "Descriptions → Sets and sequences". In the preview each item has its own Redo, Lock and filing card, next to "Redo all"; the picture send ranks the items one by one, so the best fitting version of a set is sent (a sequence still offers its next picture). Groups saved before this keep their descriptions until they are described again; "Redo out-of-date descriptions" in the settings does all the groups with one description or no story lines.

The library keeps the last 3 copies of itself (Settings → Saving and library → Library backups): one is made at the first save after 12 hours, but never when the library suddenly lost most of its pictures, and "Back up now" makes one at once. Restore puts a copy back (descriptions, roles, locks and notes; not the picture files, which "Download again" can bring back); the library as it was is kept in imagesearch-library-before-restore.json. The raw answers and full prompts shown under "How this was described" live in their own file (imagesearch-library-details.json), read in the background and only written when they change, so each library save is about half the size. The extension's lookup caches (tag aliases, implications, character genders) are kept in the browser, not in SillyTavern's settings.

Made to run on a phone: the library file is read once, and before a save it is only read again when another device changed it (the extension checks the file's tag, a tiny request); saves asked while one is running become one save; the look categories, word lists, filing-card checks and search-index hashes are worked out once and kept until they change. Requests to SillyTavern give up after a while (15 s to 3 min, by kind) and model requests after 5 minutes, so one stuck request no longer holds up every later save or description; when the library could not be read (SillyTavern restarting, say), it is read again a little later, keeping pictures added meanwhile. After a reply SillyTavern saves the chat itself, so the extension no longer saves it a second time; the settings are only saved when something in them changed.
